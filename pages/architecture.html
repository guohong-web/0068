③ 工程篇

搭建思路

"能跑"和"能维护三年"之间隔着架构。这一篇讲的是：怎么把需求翻译成一张表结构、怎么把功能拆成一层层代码、 怎么定接口规范让前后端不吵架，以及什么时候该简单、什么时候该复杂。

🧠
本篇的两个概念地基

① 分层、抽象与耦合：为什么需要分层、分层的代价是什么、什么算"低耦合高内聚"。不理解这一节，分层就只是机械照搬目录结构。
② 一致性、可用性与扩展性：CAP 定理、最终一致性、无状态设计的价值。它决定了缓存与微服务的取舍逻辑。
数据库相关名词（索引、事务、隔离级别、回表、N+1）见术语词典的数据库分类，架构类名词见架构分类。

⚠️
关于过度设计

本页会讲到微服务、消息队列、多级缓存，但请记住：一个能承载十万用户的中型系统的正确形态，往往是一个精心设计的单体应用加一台数据库。 架构的价值在于匹配当前规模，而不是展示技术广度。看到每个方案时，先问"我现在真的需要吗"。

一、动手前先回答三个问题

不写一行代码，先用一张纸回答这三问。它们决定了后面所有技术决策。

  1. 数据长什么样？

    列出所有实体（用户、订单、商品…）、每个实体的字段和类型、以及实体之间的关系（一对一/一对多/多对多）。这就是未来的表结构雏形。

  2. 数据怎么流动？

    画出关键流程：用户点击下单 → 校验库存 → 创建订单 → 扣减库存 → 发起支付 → 回调更新状态。流程里每一步失败会发生什么，就是事务和补偿逻辑的边界。

  3. 谁可以做什么？

    列出角色（游客、普通用户、管理员、运营）和每个角色能访问的操作。这是权限模型和接口鉴权的依据。

📝
极其实用的建议

把这三问的答案写成项目根目录下的 docs/design.md。三个月后接手代码的人（很可能是未来的你）会感谢这份文档。

二、分层架构：把职责切开

不管用什么语言，一个可维护的后端基本都长成这样。分层不是形式主义，而是为了让"改一处"不会牵动全身。

HTTP 请求→ 路由 Router→ 中间件→ 控制器 Controller→ 服务 Service→ 数据访问 Repository→ 数据库
层只负责不应该做
路由 / 中间件URL 映射、鉴权、日志、限流、CORS不写业务逻辑
控制器 Controller解析参数、调用 Service、组装响应不直接写 SQL，不做复杂计算
服务 Service业务规则、事务边界、编排多个数据源不感知 HTTP（不接收 req/res 对象）
数据访问 RepositorySQL / ORM 查询，返回模型对象不做业务判断
模型 / DTO数据结构定义与校验不包含数据库连接逻辑
JavaScript · 一次"创建订单"的分层走法
// ---------- routes/order.routes.js：只做路由与中间件绑定 ----------
router.post('/orders', auth, validate(createOrderSchema), orderController.create);

// ---------- controllers/order.controller.js：只做参数与响应 ----------
export async function create(req, res, next) {
  try {
    const order = await orderService.create({
      userId: req.user.id,             // 来自鉴权中间件
      items: req.body.items
    });
    res.status(201).json({ code: 0, data: order });
  } catch (err) {
    next(err);                          // 统一交给错误中间件
  }
}

// ---------- services/order.service.js：业务逻辑 + 事务边界 ----------
export async function create({ userId, items }) {
  if (!items?.length) throw new BizError(40001, '订单不能为空');

  // 事务：要么全部成功，要么全部回滚
  return db.transaction(async (tx) => {
    let total = 0;
    for (const it of items) {
      const goods = await goodsRepo.findById(it.goodsId, tx);
      if (!goods) throw new BizError(40401, '商品不存在');
      if (goods.stock < it.qty) throw new BizError(40901, `库存不足：${goods.name}`);

      await goodsRepo.decreaseStock(goods.id, it.qty, tx);   // 扣库存
      total += goods.price * it.qty;
    }
    return orderRepo.insert({ userId, items, total, status: 'PENDING' }, tx);
  });
}

// ---------- repositories/goods.repo.js：只碰数据库 ----------
export function decreaseStock(id, qty, tx) {
  // 用条件更新防超卖：影响行数为 0 说明被并发抢光了
  return tx('goods')
    .where({ id })
    .where('stock', '>=', qty)
    .decrement('stock', qty);
}
🔥
超卖的经典坑

"先查库存再扣减"在并发下必然出错：两个请求同时查到库存 1，都判断通过，最后扣成 -1。 正确做法是把判断条件写进更新语句（如上面的 where stock >= qty），或者用数据库行锁 SELECT ... FOR UPDATE，或者用乐观锁版本号。这类问题的通用名称叫竞态条件，是后端最容易出错的地方之一。

三、目录结构：让项目自己说话

两种主流组织方式，按业务复杂度选择。

按技术分层（小项目）

文件少、找东西快。项目超过 ~30 个接口后，改一个功能要横跨五个目录。

按业务模块（中大型）

每个模块自包含，改动集中在同一目录，天然适合后续拆分微服务。

四、数据库设计

数据库是项目里最难改的部分。字段加一个能接受，表结构改一次基本意味着停服。所以设计阶段多花两小时，能省掉上线后两周的加班。

建表规范

  • 每张表都有主键 id（自增或雪花 ID），不用业务字段当主键
  • 每张表都有 created_at / updated_at，排查问题时是救命稻草
  • 金额用 DECIMAL(12,2) 或整数分存储，绝不用 FLOAT
  • 时间统一存 UTC，展示时再转时区；或用 TIMESTAMP WITH TIME ZONE
  • 软删除用 deleted_at 字段而不是物理删除（保留可追溯性）
  • 状态类字段用 TINYINT + 常量注释，不用中文或魔法字符串
  • 外键约束视团队而定：强一致要求高就加，追求写入性能就用应用层保证
SQL · 一个电商核心表设计
-- 用户表
CREATE TABLE `user` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `email`       VARCHAR(120)    NOT NULL COMMENT '登录邮箱，唯一',
  `password`    VARCHAR(100)    NOT NULL COMMENT 'bcrypt 哈希值，绝不存明文',
  `nickname`    VARCHAR(50)     NOT NULL DEFAULT '',
  `status`      TINYINT         NOT NULL DEFAULT 1 COMMENT '1正常 2禁用',
  `created_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `deleted_at`  DATETIME        NULL COMMENT '非空表示已软删除',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_email` (`email`),          -- 唯一索引：从数据库层防止重复注册
  KEY `idx_created` (`created_at`)          -- 高频排序/筛选字段建索引
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

-- 订单表
CREATE TABLE `order` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_no`   CHAR(20)        NOT NULL COMMENT '对外展示的订单号，避免暴露自增 id',
  `user_id`    BIGINT UNSIGNED NOT NULL,
  `amount`     DECIMAL(12,2)   NOT NULL COMMENT '订单总额',
  `status`     TINYINT         NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已发货 3已完成 4已取消',
  `paid_at`    DATETIME        NULL,
  `created_at` DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),
  KEY `idx_user_status` (`user_id`, `status`)   -- 联合索引：查"某用户的待支付订单"
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 订单明细表：订单与商品是多对多，必须拆中间表
CREATE TABLE `order_item` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_id`   BIGINT UNSIGNED NOT NULL,
  `goods_id`   BIGINT UNSIGNED NOT NULL,
  `qty`        INT             NOT NULL DEFAULT 1,
  `price`      DECIMAL(10,2)   NOT NULL COMMENT '下单时快照价，商品改价不影响历史订单',
  PRIMARY KEY (`id`),
  KEY `idx_order` (`order_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
💰
为什么订单明细要存 price 快照

如果订单明细只存 goods_id，商品调价后历史订单金额会跟着变 —— 这是财务事故。所有"交易发生时的属性"都必须快照进订单，包括价格、名称、规格。

索引：只加该加的

规则说明
WHERE / JOIN / ORDER BY 的字段优先考虑建索引
联合索引最左前缀(a, b, c) 能命中 a、a,b、a,b,c，但命中不了 b
区分度低的字段慎建性别（只有两个值）建索引几乎无用
函数或运算会失效WHERE DATE(created_at) = '2026-01-01' 无法用索引，要写范围查询
索引有写入成本每多一个索引，插入和更新都变慢，也会占磁盘
SQL · 上生产前必做：慢查询排查
-- 开启慢查询日志，超过 0.5 秒的语句都记录下来
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';

-- 分析单条语句到底走没走索引（重点看 type 和 Extra）
EXPLAIN ANALYZE
SELECT o.id, o.amount FROM `order` o
WHERE o.user_id = 1024 AND o.status = 0
ORDER BY o.created_at DESC LIMIT 20;
-- 期望：type=ref，key=idx_user_status，Extra 不含 Using filesort
-- 危险信号：type=ALL（全表扫描）、Extra 含 Using temporary / Using filesort

-- 查看当前谁在跑长事务（排查锁等待）
SELECT id, user, time, state, LEFT(info, 80) AS sql_text
FROM information_schema.processlist
WHERE command != 'Sleep' ORDER BY time DESC;

数据库迁移（Migration）

不要手工在客户端改表 —— 你会忘记在生产上执行，或者在测试环境改错。 用迁移文件把每次结构变更写进版本控制。

Bash · 迁移工作流
# Node.js 生态：Knex / Prisma / Sequelize
npx knex migrate:make add_phone_to_user    # 生成迁移文件
npx knex migrate:latest                    # 执行未运行的迁移
npx knex migrate:rollback                  # 回滚最近一次

# Python：Alembic（配 SQLAlchemy）
alembic revision --autogenerate -m "add phone to user"
alembic upgrade head
alembic downgrade -1

# Java：Flyway（放 db/migration/V1__init.sql、V2__add_phone.sql）
./mvnw flyway:migrate

# 铁律：迁移文件只增不改；上线前先在预发环境跑一遍；
#       破坏性变更（删列/改类型）必须分两次发布（先加新列，双写，再删旧列）

五、API 设计规范

接口是前后端的契约。规范定的不是美观，而是当出错时，双方都不需要猜。

URL 与方法

操作方法 + 路径成功状态码
查询列表GET /api/v1/orders?page=1&size=20&status=0200
查询详情GET /api/v1/orders/123200
创建POST /api/v1/orders201 + Location 头
整体更新PUT /api/v1/orders/123200
局部更新PATCH /api/v1/orders/123200
删除DELETE /api/v1/orders/123204（无响应体）
子资源GET /api/v1/orders/123/items200
非 CRUD 动作POST /api/v1/orders/123/cancel200

URL 用名词复数表示资源，动作交给 HTTP 方法。无法用 CRUD 表达的动作（取消、支付、发布）用子路径 + POST，比 PATCH /orders/123 {status: 'cancel'} 更清晰、更便于加权限控制和审计日志。

状态码：不要全都返回 200

码含义什么时候用
200 / 201 / 204成功查询 / 创建 / 删除成功无返回体
400请求参数错误缺字段、格式不对、校验不过
401未认证没带 token 或 token 过期 → 前端跳登录
403无权限已登录但角色不够 → 前端提示无权限
404资源不存在ID 查不到数据
409冲突邮箱已注册、库存不足、版本冲突
422语义错误参数格式对但业务上不可接受
429请求过于频繁触发限流，响应带 Retry-After
500服务器内部错误代码异常、数据库挂了 —— 必须记日志
🚨
把错误码用对，是排查效率的分水岭

如果所有失败都返回 200 加 { success: false }，那么监控系统无法区分"正常"和"大面积报错"， 报警也没法按状态码聚合。正确使用 4xx/5xx 能让 Nginx 日志一眼看出问题类型。

统一响应结构

JSON · 约定的两种形态
// 成功
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [ { "id": 1, "amount": "99.00", "status": 0 } ],
    "page": { "current": 1, "size": 20, "total": 137 }
  },
  "requestId": "a1b2c3d4"        // 服务端生成的追踪 ID，用户报错时让他提供
}

// 失败
{
  "code": 40901,
  "message": "库存不足：机械键盘",
  "data": null,
  "requestId": "a1b2c3d4"
}

// 参数校验失败（带上字段级错误，前端可精确提示）
{
  "code": 40001,
  "message": "参数校验失败",
  "errors": [
    { "field": "email", "message": "邮箱格式不正确" },
    { "field": "items", "message": "至少选择一个商品" }
  ],
  "requestId": "a1b2c3d4"
}
🔗
requestId 是最好用的低成本设计

在入口中间件生成一个唯一 ID，写进响应头、响应体和所有日志行。用户截图报错时，你只需在日志里搜这个 ID，就能拿到这条请求经过的所有环节。 一个下午的工作量，节省以后的无数次排查时间。

分页、排序与过滤

HTTP · 查询参数约定
GET /api/v1/orders?page=2&size=20&sort=-created_at&status=0&keyword=键盘

# page/size   : 页码分页，适合后台管理（要知道总页数）
# cursor      : 游标分页，适合无限滚动（性能稳定，大偏移量不退化）
GET /api/v1/feed?cursor=eyJpZCI6MTIzfQ&limit=20

# sort 前缀 - 表示倒序，多字段用逗号分隔：sort=-status,created_at

# 响应头里带上总数，避免再发一次请求
X-Total-Count: 137

深分页陷阱：LIMIT 20 OFFSET 100000 会让数据库扫描并丢弃十万行。数据量大时改用游标分页（WHERE id < lastId ORDER BY id DESC LIMIT 20）。

六、鉴权与权限

先分清两件事：认证（Authentication）解决"你是谁"，授权（Authorization）解决"你能做什么"。新手最常犯的错是只做了认证，忘了授权 —— 于是普通用户能访问管理接口。

服务端保存会话状态，浏览器只存一个无意义的 sessionId。可以随时在服务端吊销，安全模型简单。

  • 存储Redis 或数据库；多实例部署时必须共享
  • 传输Cookie（HttpOnly + Secure + SameSite=Lax）
  • 优点可即时登出、可查看在线用户、不易被窃取后长期利用
  • 缺点需要共享存储；跨域场景配置繁琐
  • 适用传统 Web 应用、后台管理系统（同域）

服务端不存状态，所有信息放在客户端携带的签名令牌里。适合多端（App / 小程序 / 第三方）。

  • 结构header.payload.signature，payload 只是 Base64，不要放敏感信息
  • 传输Authorization: Bearer <token>
  • 有效期accessToken 短（15 分钟）+ refreshToken 长（7 天，存数据库可吊销）
  • 难点无法主动失效；需维护黑名单或用短有效期应对
  • 适用前后端分离、移动端、开放 API

RBAC = 用户 → 角色 → 权限。用户挂角色，角色挂权限码，接口声明所需权限码。

JavaScript · 权限中间件
// 权限码表：order:read / order:write / user:manage ...
function requirePerm(...codes) {
  return async (req, res, next) => {
    const perms = await getPermsByUserId(req.user.id);   // 带缓存
    const ok = codes.every(c => perms.includes(c));
    if (!ok) return res.status(403).json({ code: 40301, message: '无权限' });
    next();
  };
}

router.get('/admin/orders', auth, requirePerm('order:read'), list);
router.delete('/admin/orders/:id', auth, requirePerm('order:write'), remove);

// 数据级权限（更细）：只能看自己的数据
// 在 Service 层强制注入 user_id 条件，永远不要相信前端传来的 userId
async function getOrder(id, currentUser) {
  const order = await orderRepo.findById(id);
  if (!order) throw new NotFoundError();
  if (order.userId !== currentUser.id && !currentUser.isAdmin) throw new ForbiddenError();
  return order;
}
🔒
IDOR 越权漏洞：最常见的低级致命错误

GET /api/orders/123 里如果只用 URL 参数查数据，攻击者把 123 改成 124 就能看到别人的订单。 正确做法是每个涉及数据的查询都必须带上当前用户 ID 作为条件，或者在服务层显式校验归属。这个漏洞在真实系统里极其常见。

const hash = await bcrypt.hash(plainPassword, 12);
await userRepo.insert({ email, password: hash });

// 登录：用 compare 比对，不要自己算哈希再字符串比较

七、缓存策略

缓存是提升性能最有效的手段，也是引入 bug 最快的途径。核心矛盾永远是一致性：数据改了，缓存什么时候失效。

缓存位置典型工具适合缓存什么失效策略
浏览器Cache-Control / ETag静态资源、图片文件名加 hash，永久缓存
CDNCloudflare / 云厂商 CDN静态资源、公开接口按路径刷新或版本号
应用内进程内存 Map / LRU配置项、字典表定时刷新（多实例不一致风险）
分布式Redis / Memcached会话、热点数据、接口结果TTL + 主动删除
数据库MySQL Buffer Pool / 物化视图高频查询结果数据库自动管理
JavaScript · Cache-Aside 标准写法（最常用）
async function getGoodsDetail(id) {
  const key = `goods:detail:${id}`;

  // 1. 先查缓存
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  // 2. 缓存未命中，查数据库
  const goods = await goodsRepo.findById(id);
  if (!goods) {
    // 防穿透：空结果也要缓存，且 TTL 短，避免反复打数据库
    await redis.set(key, 'null', 'EX', 30);
    return null;
  }

  // 3. 回填缓存，随机 TTL 防止雪崩（千万个 key 同时过期）
  const ttl = 600 + Math.floor(Math.random() * 120);
  await redis.set(key, JSON.stringify(goods), 'EX', ttl);
  return goods;
}

// 更新数据时：先更新数据库，再删除缓存（不是更新缓存）
async function updateGoods(id, patch) {
  await goodsRepo.update(id, patch);
  await redis.del(`goods:detail:${id}`);        // 删除，让下次读时重建
}

缓存穿透

查询根本不存在的数据，每次都绕过缓存打到数据库。对策：缓存空值、布隆过滤器、参数合法性校验。

缓存击穿

某个热点 key 过期瞬间，大量请求同时涌向数据库。对策：热点 key 永不过期 + 后台更新，或加互斥锁只放一个请求去重建。

缓存雪崩

大批 key 同一时刻失效，数据库瞬间被压垮。对策：TTL 加随机值、多级缓存、限流降级。

一致性延迟

更新数据库后删除缓存，理论上仍有极短不一致窗口。对金额等强一致场景，直接读库或用分布式锁，不要依赖缓存。

八、单体还是微服务

这是最容易被过度讨论的问题。给一个明确的判断标准：

📐
决策原则

团队人数 < 10 人，或日活 < 10 万 → 单体应用。一个代码库、一次部署、一个数据库。
当出现以下信号再考虑拆分：① 不同模块的伸缩需求差异巨大（图片处理 vs 订单查询）；② 发布互相阻塞，A 团队等 B 团队；③ 单个模块的故障拖垮全站。

维度单体应用微服务
开发效率高（无跨服务调试）低（需服务发现、链路追踪）
部署复杂度低（一个包）高（N 个服务编排）
事务一致性数据库事务直接搞定需 Saga / TCC / 消息最终一致
故障隔离差（一处崩溃全站挂）好（单服务故障可降级）
技术异构难易（每个服务可选不同语言）
运维成本1 套监控N 套服务 + 网关 + 注册中心

务实的三步走路径

  1. 阶段一：模块化单体

    一个应用，但代码严格按业务模块分目录，模块间只通过明确的内部接口调用。这是 90% 项目的正确终点。

  2. 阶段二：抽出独立部署单元

    把资源消耗大或伸缩需求不同的部分（图片处理、定时任务、报表导出）拆成独立进程，其余保持单体。

  3. 阶段三：真正的服务化

    引入网关、服务注册、配置中心、链路追踪。此时必须有专职团队维护基础设施，否则得不偿失。

密钥泄露是最高频的严重事故

把密钥提交到 Git 后，即使删除文件，历史记录里依然存在，公开仓库会被爬虫秒抓。 一旦泄露：第一时间在服务商后台轮换（重新生成）密钥，而不是只删代码。清理历史需要 git filter-repo 重写全部提交，且已 fork 的仓库无法回收。

统一日志与错误处理

JavaScript · 结构化日志 + 全局错误处理
import pino from 'pino';
const log = pino({ level: process.env.LOG_LEVEL || 'info' });

// 结构化日志：输出 JSON，方便日志系统按字段检索聚合
log.info({ requestId, userId, path: req.path, ms: 42 }, 'request done');
log.error({ requestId, err: err.message, stack: err.stack }, 'order create failed');

// 自定义业务错误类，携带可对外暴露的错误码与状态码
export class BizError extends Error {
  constructor(code, message, status = 400) {
    super(message);
    this.code = code;
    this.status = status;
  }
}

// 全局错误中间件：必须是最后一个注册的中间件
app.use((err, req, res, next) => {
  const status = err.status || 500;
  log.error({ requestId: req.id, path: req.path, err: err.message, stack: err.stack },
            status >= 500 ? 'server error' : 'client error');

  res.status(status).json({
    code: err.code || 50000,
    // 关键：5xx 不把内部错误细节返回给客户端，避免泄露表名、路径等信息
    message: status >= 500 ? '服务器繁忙，请稍后重试' : err.message,
    requestId: req.id
  });
});

// 进程级兜底：避免未捕获异常导致静默退出或状态不明
process.on('unhandledRejection', (r) => log.fatal({ r }, 'unhandledRejection'));
process.on('uncaughtException', (e) => {
  log.fatal({ e }, 'uncaughtException');
  process.exit(1);              // 交给容器编排重启，比带病运行安全
});

十、常见架构反模式

在循环里查数据库（N+1 查询）

先查 100 个订单，再逐个查每个订单的用户名 —— 一共 101 次查询。正确做法是一次性把 userId 收集起来，用 IN 批量查询后内存里做映射。接口从 3 秒优化到 50 毫秒，往往就靠改这一处。

把业务逻辑写在控制器里

控制器直接写 SQL 和业务判断，导致逻辑无法复用、无法测试、换个入口（如定时任务）就得复制一遍。业务逻辑必须在 Service 层。

用 SELECT * 查询

多余字段浪费网络与内存，且表结构变更时容易出错。明确列出需要的字段，尤其是含有大文本（TEXT/BLOB）的表。

长事务

事务里调用第三方接口、发邮件、处理图片 —— 事务持续几秒甚至几十秒，期间持有行锁，会迅速造成锁等待雪崩。事务只包住数据库操作，外部调用放到事务提交之后（可用消息队列或事件机制）。

在数据库里存业务格式化数据

把金额格式化成 "¥99.00" 存起来、把日期格式化成 "2026年9月18日" 存起来 —— 一旦要换展示格式或做计算就只能全表更新。数据库存原始值，格式化交给前端。

过早抽象

为了"以后可能复用"设计三层泛型工厂 + 抽象基类，结果只有一个实现。抽象应该从第二个重复出现时开始，而不是从第一个开始。

没有健康检查接口

容器编排、负载均衡、监控都需要一个能判断"服务是否可用"的端点。GET /healthz 应同时检查数据库和 Redis 连通性，返回 200 或 503。

JavaScript · 一个合格的健康检查
app.get('/healthz', async (req, res) => {
  const checks = {};
  let healthy = true;

  try {
    await db.raw('SELECT 1');
    checks.database = 'ok';
  } catch (e) {
    checks.database = 'fail: ' + e.message;
    healthy = false;
  }

  try {
    await redis.ping();
    checks.redis = 'ok';
  } catch (e) {
    checks.redis = 'fail: ' + e.message;
    healthy = false;
  }

  checks.uptime = Math.round(process.uptime()) + 's';
  checks.version = process.env.APP_VERSION || 'dev';

  res.status(healthy ? 200 : 503).json({ status: healthy ? 'ok' : 'degraded', checks });
});
