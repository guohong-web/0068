原理与概念

技术名词每天都在变，底层的性质与原理几十年没变。 这一篇不教任何具体语法，只讲清楚 Web 是什么、协议是怎么工作的、计算机是怎么同时干很多事的、系统为什么需要分层。 学完之后再看后面五章，你会发现所有工具都只是这些原理的具体实现。

一、Web 的本质：请求—响应模型

网站到底是什么Website / Web Application

定义网站是一套运行在服务器上的程序，它把一堆资源用统一的地址标识出来，并用统一的协议对外提供访问。

三个要素① 资源（一个页面、一段数据、一张图片）；② 地址（URL，用来唯一指认资源）；③ 协议（HTTP，规定怎么请求、怎么回应）。

性质Web 天生是分布式的（代码和数据不在一台机器上）、无状态的（每个请求互相独立）、基于文本的（HTTP 报文是人类可读的文本）。这三条性质解释了后面几乎所有设计问题。

⚠️
最常见的认知错误

初学者常把"网站"理解成"一堆 HTML 文件放在机器上"。这只对静态网站成立。 真正的 Web 应用，服务器上跑的是一个持续运行的进程，它收到请求后现场计算、查数据库、拼装结果再返回 —— 同一个 URL 在不同时间、不同用户下返回的内容可以完全不同。

静态网站、动态网站、Web 应用的区别

类型本质内容如何产生典型例子
静态网站一批预先写好的文件作者手写，服务器只负责原样发送个人博客、产品文档、公司官网介绍页
动态网站程序 + 模板 + 数据库服务器每次请求时用模板拼出 HTML新闻站、论坛、企业后台（服务端渲染）
Web 应用前端程序 + 后端 API + 数据库后端只返回数据，页面由浏览器端程序渲染在线文档、管理系统、聊天工具

三者的界线是模糊的，很多项目是混合的：首屏用服务端渲染，交互部分用前端程序接管。理解这个分类的意义在于 —— 它会直接决定你的部署方式（静态托管 vs 需要服务器）。

客户端 / 服务器模型

客户端 Client

  • 主动发起请求的一方
  • 浏览器、手机 App、小程序、另一个后端服务
  • 数量多、环境不可控、可能被恶意篡改
  • 因此：永远不要信任客户端传来的任何数据

服务器 Server

  • 被动等待并响应请求的一方
  • 一台机器上可以同时跑多个服务
  • 环境可控、性能有限、需要保护
  • 因此：所有校验、权限、限额都必须在服务端做

B/S 架构与 C/S 架构Browser-Server / Client-Server

B/S客户端是浏览器。用户无需安装，升级只需改服务器。代价是能力受浏览器沙箱限制（不能随意读写本地文件、不能后台常驻）。

C/S客户端是专门的安装程序（如桌面软件、手机 App）。能力强、体验好，但需要分发与更新、要适配多个平台。

趋势两者在融合：Web 端通过 PWA、WebAssembly 越来越"像原生应用"，原生端大量使用 WebView 嵌入网页。

URL 的解剖

一个完整 URL 的组成部分
https://user:pass@app.example.com:443/api/v1/orders/123?status=0&page=2#detail
└──┬─┘ └───┬───┘└───────┬───────┘└┬┘└────────┬────────┘└────┬────┘└──┬─┘
 协议    认证信息      主机/域名      端口      路径 Path      查询串    片段

协议 Scheme      用什么规则通信：http / https / ws / ftp
主机 Host        目标机器的名字，需要经 DNS 解析成 IP
端口 Port        一台机器上的"门牌号"，用于区分不同服务。http 默认 80，https 默认 443
路径 Path        资源的层级位置，服务端的路由就是靠它来匹配
查询串 Query     以 ? 开头、& 分隔的键值对，用于筛选、分页、排序
片段 Fragment    以 # 开头，只给浏览器看，永远不会发送到服务器

记住最后一条很重要：前端用 # 做路由（Hash 路由）就是因为这部分变化不会触发新的网络请求。

一次访问，完整经过了多少环节

从输入网址到看到页面
① 你在地址栏输入 app.example.com
        ↓
② 浏览器查缓存：本地 DNS 缓存 → 系统 hosts → 路由器 → 运营商 DNS
        ↓  都没有才发起真正的 DNS 查询
③ DNS 递归查询：根域名服务器 → .com 顶级域 → example.com 权威服务器 → 得到 IP
        ↓
④ 建立 TCP 连接（三次握手）：客户端 SYN → 服务端 SYN+ACK → 客户端 ACK
        ↓
⑤ TLS 握手：校验证书 → 协商密钥（HTTPS 才有这一步）
        ↓
⑥ 浏览器发出 HTTP 请求：GET / HTTP/1.1  + 请求头
        ↓
⑦ 请求到达机房：可能先经过 CDN 边缘节点 / 负载均衡器
        ↓
⑧ Web 服务器（Nginx）判断：是静态文件就直接返回，是接口就转发给应用
        ↓
⑨ 应用服务器执行代码：鉴权 → 业务逻辑 → 查询缓存 → 查询数据库
        ↓
⑩ 数据库返回数据（磁盘 IO → 内存 → 网络）
        ↓
⑪ 应用拼装 JSON / HTML，带上响应头返回
        ↓
⑫ 浏览器解析 HTML → 构建 DOM → 计算样式 → 布局 → 绘制 → 显示
        ↓
⑬ 页面里的 JS 继续发起接口请求，拿到数据后局部更新界面

其中任何一跳失败，用户看到的结果都是"打不开" ——
而这 13 个环节里，只有 ⑧⑨⑩ 是你写的代码，其余都属于"必须理解的基础设施"。

无状态Stateless

定义服务端不保存与客户端交互的历史记忆。每个请求都是独立的，服务端只根据本次请求携带的信息来决定如何处理。

性质这是 HTTP 协议的设计选择，不是缺陷。无状态让服务器可以随意重启、随意水平扩容：任意一台机器都能处理任意一个请求，因为大家不需要共享"谁登录了"这份记忆。

后果代价是每次请求都要重复携带身份信息（Token / Cookie），而且无法天然实现"登录状态""购物车"。于是人类发明了 Cookie、Session、Token 来在无状态协议之上"假装有状态" —— 详见 第七节。

二、网络分层与协议

协议Protocol

定义通信双方事先约定好的一套规则，规定数据的格式、顺序和含义。就像两个人约定用中文、按"问—答"的顺序交流。

性质协议必须是双方共识，且必须可分层。你可以换掉发送内容的语言（应用层），而不影响邮政系统怎么送信（传输层）—— 这正是分层思想的价值。

为什么要分层

把"从一台电脑传数据到另一台电脑"这一件事拆成若干层，每层只解决一个问题、只依赖下一层提供的能力。 好处有三条：① 每层可以独立替换（WiFi 换成光纤，上面的 HTTP 一行代码不用改）； ② 每层可以独立优化（专门做 CDN 的公司只需关心传输与缓存）； ③ 故障可以按层定位（ping 通但网页打不开，说明问题不在网络层）。

🧪
用分层思维排查问题

网站打不开时，从下往上逐层验证，第一层失败的地方就是问题所在：
ping（网络层）→ nc -zv host 443（传输层端口）→ curl -I（应用层协议）→ 看响应内容（业务层）。
这个顺序能让你在 30 秒内判断"是 DNS 问题、网络问题、还是代码问题"，而不是盲目重启服务器。

DNSDomain Name System

定义把域名翻译成 IP 地址的系统。它是一个全球分布、分层授权的数据库，没有单一中心节点。

性质分层授权：根服务器只管 .com 在哪，.com 只管 example.com 在哪，最终的答案由域名所有者自己的权威服务器给出。可缓存：每一层都可以缓存结果（缓存时长由 TTL 决定），这是它能扛住全球查询量的原因。

为什么重要换服务器、做灰度、上 CDN，本质都是在改 DNS 或让 CDN 通过 CNAME 接管解析。理解 TTL 是理解"为什么改了解析没立刻生效"的前提。

TCP 与 UDP：两种传输性质

TCP · 可靠但重

  • 面向连接：先握手建立连接再传数据
  • 保证顺序、保证不丢、保证不重复
  • 有流量控制与拥塞控制，会自动降速
  • 代价：延迟更高，头部开销更大
  • 用于：网页、接口、文件传输、数据库

UDP · 快但不可靠

  • 无连接：直接发，不等对方回应
  • 不保证顺序、不保证送达
  • 没有拥塞控制，想发多快发多快
  • 优点：延迟低，头部只有 8 字节
  • 用于：DNS 查询、视频直播、游戏、HTTP/3

"可靠"不是免费的：TCP 的可靠性靠重传和确认实现，代价是延迟。直播宁可丢几帧也不能卡顿，所以选 UDP；下载文件不能缺字节，所以选 TCP。这就是性质决定选型的典型例子。

三次握手为什么是三次

目的让双方都确认两件事：我的发送能力正常、你的接收和发送能力都正常。

过程① 客户端发 SYN（我能发，你在吗）→ ② 服务端回 SYN+ACK（我在，我也能发）→ ③ 客户端回 ACK（我收到了）。

为什么不能两次如果只握两次，服务端无法确认客户端收到了自己的回应，也无法确认客户端的接收能力。而且历史上两次握手会因"过期请求"造成服务端建立无用连接。三次是验证双向能力的最小次数。

四次挥手关闭连接时，一方说"我没数据要发了"，另一方可能还有数据要发，所以要分开发送确认和关闭请求，共四次。这解释了大量 TIME_WAIT 连接的由来。

三、HTTP 协议的性质

HTTPHyperText Transfer Protocol

定义应用层的请求—响应协议，规定客户端如何描述"我要什么"，服务端如何描述"结果是什么"。

性质一：基于文本报文是纯文本，人类可读、易调试（这是它能统治世界的重要原因）。

性质二：无状态服务端不记请求之间的关联，见前文。

性质三：可扩展通过头部字段可以无限扩展语义，不需要改协议本身。几乎所有的工程实践（缓存、鉴权、跨域、灰度）都靠头部字段实现。

报文结构

请求报文与响应报文
【请求】                                    【响应】
POST /api/v1/orders HTTP/1.1     ← 请求行    HTTP/1.1 201 Created          ← 状态行
Host: api.example.com            ┐         Content-Type: application/json ┐
Content-Type: application/json   │ 请求头   Cache-Control: no-store         │ 响应头
Authorization: Bearer eyJhbG...  │         X-Request-Id: 8f3a-2b1c          │
User-Agent: Mozilla/5.0          ┘         Set-Cookie: sid=abc; HttpOnly    ┘
                                          ← 空行（分隔头与体）
← 空行（必须，用于分隔头与体）              {"id":1024,"amount":"99.00"}
{"items":[{"goodsId":778,"qty":2}]}   ← 请求体

注意那个"空行"：它是真实的协议要求。少了它，服务器会把请求体当成头部字段继续解析，导致各种莫名其妙的错误。

方法（Method）的语义

HTTP 方法不只是"不同名字"，它们有严格定义的性质，中间件、缓存、爬虫都依赖这些性质做判断。

方法语义安全（不改数据）幂等（执行多次结果相同）可缓存
GET获取资源是是是
HEAD只取响应头是是是
POST创建资源 / 执行动作否否否
PUT整体替换资源否是否
PATCH局部更新资源否通常否否
DELETE删除资源否是否

幂等性Idempotence

定义同一个操作执行一次和执行多次，对系统状态的影响相同。"给订单打上「已支付」"是幂等的；"余额减 10 元"不是。

为什么重要网络一定会出现"请求发出去了但响应没回来"的情况。客户端不确定是否成功，就会重试。如果接口不幂等，一次重试就可能重复扣款。

工程做法① 用幂等键（Idempotency-Key 头 + 唯一索引）；② 用状态机约束流转（已支付的订单不能再支付）；③ 用数据库唯一约束兜底。

状态码的五大类

类别含义责任方常见
1xx信息性，请求已收到正在处理—101 协议切换（WebSocket）
2xx成功—200 OK、201 Created、204 No Content
3xx重定向，需要再发一次请求—301 永久、302 临时、304 走缓存、307 保方法
4xx客户端错误调用方400、401、403、404、409、429
5xx服务端错误服务方500、502、503、504

4xx 与 5xx 的区分极其重要：它决定了"该谁去修"。监控系统通常只对 5xx 报警，因为 4xx 是用户用错了（或攻击探测），5xx 才是自己坏了。

头部方向作用

连接管理：从短连接到多路复用

HTTP 各版本的连接性质演进
HTTP/1.0  每个请求新建一个 TCP 连接，用完就关
          请求1 ──握手──发送──响应──关闭
          请求2 ──握手──发送──响应──关闭      三次握手很贵，浪费严重

HTTP/1.1  长连接（Keep-Alive）+ 管道化
          握手──┬──请求1──响应1
                ├──请求2──响应2        └── 但响应必须按顺序返回
                └──请求3──响应3            前一个慢，后面全部排队等待
                                         ← 这就是"队头阻塞"

HTTP/2    二进制分帧 + 多路复用
          握手──┬──请求1 ─┐
                ├──请求2 ─┼── 交错传输，谁先准备好谁先回
                └──请求3 ─┘        ← 应用层队头阻塞被解决
                                 ← 但 TCP 层一旦丢包，所有流仍要等待

HTTP/3    基于 QUIC（跑在 UDP 上）
          握手（0-RTT 或 1-RTT）── 各流独立，丢包只影响自己
          ← 彻底解决传输层队头阻塞，弱网环境提升明显
🚀
这条演进线带来的实践结论

① 开 HTTPS 不只是为了安全，还因为 HTTP/2、HTTP/3 基本上只在 HTTPS 下启用；
② 老项目用"域名分片 / 雪碧图"来绕过 1.1 的并发限制，在 HTTP/2 下这些优化反而有害（失去了多路复用的收益）；
③ 现代前端"代码分割 + 懒加载"之所以可行，前提是 HTTP/2 让多个小文件的并发请求不再昂贵。

常见误解：GET 不能带请求体？

协议并没有禁止 GET 带 body，但语义上未定义，很多服务器、代理、缓存会直接丢弃它。所以工程上的结论是：GET 不应依赖请求体传递数据，需要传复杂条件时改用 POST，或把条件编码进查询串。

常见误解：返回 200 就是成功了？

很多老系统习惯"永远返回 200 + body 里写 success: false"。这让缓存、代理、监控全部失去判断依据。正确做法是让状态码承担语义，body 只承载业务数据与错误明细。

常见误解：304 表示没改所以不返回内容？

正确。304 是协商缓存的结果：浏览器带着 If-None-Match 问"我这份还有效吗"，服务器答"有效"，于是浏览器直接用本地副本。它确实省了带宽，但依然发生了一次完整的网络往返 —— 所以更强的做法是让浏览器在有效期内完全不发请求（强缓存）。

四、HTTPS 与加密

HTTPSHTTP over TLS

定义HTTP 加上 TLS 加密层，即 HTTP + 加密 + 身份认证 + 完整性校验。

它解决三个问题 ① 机密性：中间人抓包看不到明文（防运营商劫持插广告）； ② 完整性：内容被篡改能被发现； ③ 身份认证：确认你连的确实是 example.com，而不是伪装的钓鱼站。

性质HTTP 本身不加密，HTTPS 是在 HTTP 和 TCP 之间插了一层 TLS。对上层应用来说，HTTP 的语义完全不变 —— 所以"支持 HTTPS"通常只需要改服务器配置，不需要改代码。

三种密码学工具的性质对比

工具性质速度能否解密用途
对称加密
AES、ChaCha20		同一把密钥加解密快能（有密钥）加密实际传输的数据
非对称加密
RSA、ECC		公钥加密、私钥解密（或反之签名）慢（约慢千倍）私钥持有者能安全地在网络上交换密钥、做数字签名
哈希
SHA-256、bcrypt		单向，不可逆快（bcrypt 故意慢）不能存储密码、校验文件完整性

为什么"用非对称加密传输对称密钥"

矛盾非对称加密安全，但太慢，不适合加密整站流量；对称加密快，但双方怎么安全地约定同一把密钥？在网上直接传就会被人截获。

解法用非对称加密只传那一小段密钥（几 KB，慢也无所谓），然后用这把对称密钥加密之后所有数据（几十 MB，必须快）。这就是 TLS 握手的核心思想，也是"混合加密"的由来。

举一反三这种"用重武器解决小问题，用小武器解决大问题"的思路在工程中非常常见：用数据库事务保证关键的余额变更，用消息队列处理海量的日志写入。

为什么"忽略证书警告"是危险的

证书链的信任来源是操作系统/浏览器内置的受信任 CA 列表。如果证书是自签的或签发者不在列表里，浏览器无法确认对方身份。 你在公共 WiFi 下点了"继续访问"，就等于同意和一个未知中间人通信 —— 这正是中间人攻击最常用的入口。生产环境的正确做法是申请免费证书（Let's Encrypt），而不是让用户无视警告。

证书链与 CACertificate Authority

定义CA 是受信任的第三方，用自己的私钥给你的公钥"签字"，证明"这把公钥确实属于 example.com"。

信任链根 CA（内置在系统里）→ 中间 CA → 你的站点证书。校验时逐级往上验签，直到根证书。这就是为什么 Nginx 配置必须用 fullchain.pem（含中间证书）—— 少了中间证书，部分设备就无法完成信任链拼接。

推论如果某个根 CA 被攻破，全球该 CA 签发的所有证书都会失效。所以历史上出现过 CA 被吊销、浏览器紧急更新的安全事件。

常见误解：HTTPS 会拖慢网站

握手确实增加了一次往返（TLS 1.3 已优化到 1-RTT，复用会话可 0-RTT），但数据加密本身在现代 CPU 上有 AES-NI 硬件加速，开销很小。 而 HTTP/2、HTTP/3 带来的多路复用收益通常远大于握手的成本 —— 实测中启用 HTTPS + HTTP/2 的页面往往更快。

常见误解：有了 HTTPS 网站就安全了

HTTPS 只保护传输过程。它不能防 SQL 注入、不能防越权访问、不能防服务器被入侵、也不能阻止服务端自己把数据泄露出去。 它解决的是"路上安全"，不是"屋里安全"。两者缺一不可。

常见误解：证书要花钱买

Let's Encrypt 从 2015 年起提供免费 DV 证书，自动化签发与续期，覆盖了绝大多数场景。付费证书的差异主要在保修金额、组织信息（OV/EV）和商业支持上，对普通项目没有实际收益。

五、数据、编码与序列化

字符、码点与编码Character / Code Point / Encoding

字符集 CharSet一套字符的集合。ASCII 只有 128 个（英文 + 控制符），Unicode 收录了十几万个字符（含全球文字与 emoji）。

码点 Code Point字符在字符集里的编号。汉字"中"的码点是 U+4E2D。

编码 Encoding把码点变成字节序列的规则。UTF-8 是最主流的编码：英文 1 字节、汉字 3 字节、emoji 4 字节，且与 ASCII 完全兼容。

结论现在几乎所有项目都应该统一使用 UTF-8，包括数据库、连接、文件、HTTP 头。只要有一处不是 UTF-8，就会出现"乱码"。

乱码的三种成因

  • 编码不一致：数据以 GBK 写入、以 UTF-8 读取。表现为大量"锟斤拷"或问号。
  • 编码声明缺失：HTML 没写 meta charset，HTTP 响应头也没写，浏览器只能猜，猜错就乱。
  • 二次转码：数据被解码成错误的字符后又被重新编码，属于不可逆损坏，只能重新输入。

排查顺序永远是：数据库字符集 → 连接字符集 → 响应头 → HTML meta。用 SHOW VARIABLES LIKE 'character%' 一次看完 MySQL 的四层设置。

序列化Serialization

定义把内存里的数据结构（对象、数组）转换成可以在网络上传输或写入磁盘的字节序列；反向过程叫反序列化。

性质序列化格式的能力与体积是一对矛盾：能力越强（类型、引用、二进制）体积越小但可读性越差；越简单可读（纯文本）体积越大但易调试。

格式类型可读性体积典型场景
JSON文本极好中Web 接口事实标准，浏览器原生支持
Form（表单）文本好小HTML 表单提交、简单登录
XML文本好（冗长）大传统企业接口、配置文件、SOAP
Protobuf二进制差（需 schema）很小服务间高性能通信（gRPC）
MessagePack二进制差小需要比 JSON 更省带宽的场景
🧩
为什么 JSON 赢了

不是因为最快或最小，而是因为浏览器原生就能解析（JSON.parse 比 eval 安全且快）、人类可读、且几乎所有语言都有成熟库。 再一次印证：工程上的胜利通常来自"总体成本最低"，而不是"单项指标最好"。

MIME 类型与 Base64

MIME用 类型/子类型 描述内容格式，如 text/html、application/json、image/png。它是"这段字节该怎么解释"的说明书，弄错会导致浏览器下载而不是显示文件。

Base64把任意二进制数据用 64 个可打印字符表示，体积增大约 33%。因为 HTTP 头、URL、JSON 都是文本环境，无法直接放二进制，所以图片内联、JWT 的 payload、邮件附件都使用 Base64。它只是编码，不是加密 —— 任何人都能还原。

六、进程、线程与并发

程序 / 进程 / 线程 / 协程

程序磁盘上的静态文件，只是一堆指令。

进程程序的一次运行实例，拥有独立的内存空间。进程之间默认互不可见（安全，但通信成本高）。

线程进程内的执行单元，共享同一份内存。共享让通信变快，也让"同时改一个变量"成为可能 —— 竞态问题由此而来。

协程用户态的轻量执行单元，由程序自己调度，切换成本远低于线程。Go 的 goroutine、Python 的 async、JS 的 async/await 本质都是这一层抽象。

维度进程线程协程
内存隔离完全隔离共享共享
创建开销高（毫秒级）中（微秒～毫秒）极低（纳秒级）
可同时存在数量几十～几百几百～几千几万～几十万
切换由谁决定操作系统操作系统（抢占式）程序（协作式）
崩溃影响只影响自己拖垮整个进程拖垮整个进程
适合隔离、独立部署CPU 密集计算大量 IO 等待

并发与并行Concurrency vs Parallelism

并发一种结构：让程序能够同时处理多个任务（交替推进）。单核 CPU 也能并发。

并行一种物理现实：多个任务在同一时刻真正同时执行，需要多核。

类比一个厨师同时做三道菜是并发（切菜的间隙去看汤），三个厨师各做一道菜是并行。并发解决的是"等待时间不要浪费"，并行解决的是"算力不够"。

对 Web 的意义Web 服务绝大多数时间是在等（等数据库、等外部接口），属于 IO 密集。所以最重要的能力是"并发"而不是"并行" —— 这就是 Node.js 单线程也能扛住高并发的原因。

同步 / 异步 / 阻塞 / 非阻塞

这四个词经常被混用，但它们描述的是两件不同的事：

概念描述的问题含义
同步 / 异步调用方要不要等结果同步：调用后必须等返回；异步：调用后立即继续，结果稍后通过回调/事件通知
阻塞 / 非阻塞等待期间线程能不能干别的阻塞：线程挂起干等；非阻塞：调用立刻返回"还没好"，线程可以去做别的事

同步阻塞（最传统）

  • 读数据库 → 线程挂起 → 数据回来 → 继续
  • 实现简单、逻辑直观
  • 一个线程只能服务一个请求，高并发需要大量线程
  • 典型：PHP-FPM、Java 传统 Servlet

异步非阻塞（现代主流）

  • 发起读 → 立刻返回 → 去处理别的请求 → 数据好了再回调
  • 少量线程即可支撑海量连接
  • 代码需要 async/await 才易读，调试稍难
  • 典型：Node.js、Go、Nginx、Python asyncio
事件循环（Event Loop）的工作原理
   ┌──────────────────────────────────────────────┐
   │                                              │
   ▼                                              │
[ 1. 取出待执行的回调 ]                            │
   │        ↑                                      │
   │     （没有任务就等待）                          │
   ▼                                              │
[ 2. 执行回调，直到当前任务完成 ]                    │
   │  这一步是"单线程"的：任何同步代码都会卡住整个循环   │
   ▼                                              │
[ 3. 执行所有微任务（Promise.then / queueMicrotask）]│
   │  ← 微任务队列会在本轮清空，且优先级高于宏任务      │
   ▼                                              │
[ 4. 交给系统内核处理 IO（请求数据库/文件/网络）]      │
   │  这一步不占用 JS 线程                          │
   ▼                                              │
[ 5. 把已完成的 IO 回调排进队列 ]─────────────────────┘

由此可推出两条极其重要的实践结论：
  · 不要在请求处理里写 CPU 密集的同步代码（大循环、大 JSON 解析、图片处理）
    → 它会阻塞整个进程，导致所有其他请求全部卡住
  · 单进程只能用一个 CPU 核心
    → 要用满多核必须起多个进程（PM2 cluster / 多容器 / Go 的 GOMAXPROCS）

竞态条件Race Condition

定义多个执行单元以不可预期的顺序访问共享数据，导致结果依赖于"谁先谁后"。典型是"查库存 → 判断 → 扣减"三步之间被插入另一个请求。

性质它的可怕之处在于：测试环境几乎永远复现不出来，只在压力大、并发高时偶发。所以不能靠"多测几次"，必须从机制上消除。

消除手段① 让判断与更新在一条原子语句里完成（UPDATE ... WHERE stock >= n）；② 加锁（数据库行锁 / 分布式锁）；③ 乐观锁版本号；④ 用队列把并发请求串行化。

死锁Deadlock

定义两个或更多执行单元互相持有对方需要的资源，且都不释放，导致永久等待。A 拿了锁 1 等锁 2，B 拿了锁 2 等锁 1。

预防① 约定加锁顺序（大家都按 id 从小到大加锁）；② 设置锁等待超时（超时即失败重试）；③ 缩小锁范围、缩短事务时长。数据库通常能自动检测死锁并回滚其中一个事务，所以你的代码要能正确处理"被数据库回滚"这种失败并重试。

CPU 密集 vs IO 密集 —— 一个决定选型的判断

CPU 密集任务时间主要花在计算上（加密、图像压缩、大数运算、报表统计）。优化方向：多进程/多线程、用更快的语言、做缓存避免重复计算。

IO 密集任务时间主要花在等待上（查库、调接口、读写文件）。优化方向：异步、连接池、并发请求、加缓存减少 IO 次数。

为什么这是最重要的判断它直接解释了前一篇的选型结论：Node.js / Python 适合 IO 密集（异步模型优秀），Java / Go 在 CPU 密集与高并发下更稳，Rust 在有极致性能要求时才有价值。先判断自己的任务性质，再选工具，而不是反过来。

🧠
关于 GIL 这个高频面试概念

CPython 有全局解释器锁（GIL），同一进程内同一时刻只有一个线程能执行 Python 字节码。这导致 Python 多线程无法并行做 CPU 密集任务。 但它不影响 IO 密集场景：线程在做 IO 时会释放 GIL，所以多线程爬虫、多线程调接口依然有效。需要真并行时用多进程（multiprocessing）或原生扩展。

七、状态与身份识别

有状态与无状态：为什么它决定架构

有状态服务服务端保存了与某个客户端相关的会话数据（比如内存里的 session）。后果：同一个用户的后续请求必须打到同一台机器，否则状态找不到。

无状态服务每个请求自带全部所需信息。后果：任意实例都能处理任意请求，可以随意增加、删除、重启实例。

状态放在哪里，决定了能不能水平扩展
【有状态：状态存在应用内存里，无法随意扩容】
   用户 ──→ 负载均衡 ──→ 实例A（内存里有 session）
                 └──→ 实例B（内存里没有 session）← 用户被分到这里就掉登录
   要让 A 和 B 一致，只能做"会话粘滞"或进程间同步 → 扩容变得很麻烦

【无状态：状态外置到共享存储】
   用户 ──→ 负载均衡 ──┬──→ 实例A ┐
                      ├──→ 实例B ├──→ Redis / 数据库（唯一的真相来源）
                      └──→ 实例C ┘
   实例可以随便加，甚至随时被杀死重建，用户毫无感知
   ← 这就是"把状态赶到边界之外"这一架构原则的具体体现

Cookie / Session / Token / JWT 的关系

概念它是什么存在哪关键性质
Cookie浏览器提供的一种存储与自动携带机制浏览器（会在请求时自动带上）只是一个"容器"，不规定里面装什么
Session服务端保存的会话数据服务端（内存 / Redis / 数据库）浏览器只拿一个无意义的 sessionId，可随时在服务端吊销
Token一张代表身份的凭证（内容自定）客户端（内存 / localStorage）需要前端显式放进请求头，不自动携带
JWT一种特定格式的 Token（头部.载荷.签名）客户端自包含：服务端验签即可确认身份，无需查库 → 无状态
🔍
选择的标准：你要不要"主动踢人下线"

JWT 的载荷是 Base64 编码的明文，服务端不存储，所以签发后在过期前无法撤销。如果你的业务需要"管理员强制下线""改密码后立即失效所有设备"，纯 JWT 就做不到，只能： ① 用 Redis 维护黑名单（那就变成有状态了）；② 用短有效期 accessToken + 可撤销的 refreshToken；③ 回到 Session。 没有更优，只有取舍。

浏览器存储方式对比

方式容量生命周期会随请求发送吗能否被 JS 读取
Cookie约 4KB可设置过期时间会（自动）取决于 HttpOnly
localStorage约 5MB永久，除非手动清除不会能
sessionStorage约 5MB关闭标签页即清空不会能
IndexedDB几百 MB～GB永久不会能（异步 API）

一个重要的安全推论：放在 localStorage 的 Token 一旦网站存在 XSS 漏洞就会被直接偷走； 放在 HttpOnly Cookie 里的凭证 JS 读不到，但又要面对 CSRF 风险（需要 SameSite 缓解）。 两种方案各有软肋，这也是"没有绝对安全的存储"这一事实的体现。

八、页面是怎么生成的

同一个页面，可以在服务器上生成 HTML 后发给浏览器，也可以在浏览器里用 JS 现场拼出来。 这个选择叫渲染模式，它直接影响首屏速度、SEO 和服务器成本。

四种渲染模式的数据流
【CSR 客户端渲染】浏览器先下载空壳，再靠 JS 拉数据渲染
浏览器 ──请求──→ 服务器 ──返回几乎空白的 HTML + 大体积 JS──→ 浏览器
       └─ JS 下载执行 ─→ 发起接口请求 ─→ 拿到数据 ─→ 渲染出内容
       缺点：首屏慢（白屏）、SEO 差；优点：后续跳转极快，服务器压力最小

【SSR 服务端渲染】每次请求都在服务器上现场拼好 HTML
浏览器 ──请求──→ 服务器 ─(查数据 + 渲染HTML)─→ 返回完整 HTML
       └─ 浏览器直接显示 ─→ JS 下载后"接管"页面（水合）
       优点：首屏快、SEO 好；缺点：服务器每次都要渲染，压力大

【SSG 静态生成】构建时就把 HTML 生成好，当作静态文件托管
构建阶段 ─(渲染所有页面)─→ 一堆 HTML 文件 ─→ CDN
       └─ 用户访问时等同于访问静态文件（极快、几乎零成本）
       缺点：内容更新需要重新构建；适合博客、文档、官网

【ISR 增量再生】SSG 的升级：静态文件按需/定时重新生成
       └─ 用户访问到过期页面时，后台重新生成，先返回旧版本
       优点：兼顾静态的速度与内容的时效性
模式首屏速度SEO服务器成本适用
CSR慢（白屏）差最低登录后的内部系统、后台管理
SSR快好高电商、内容平台、需要 SEO 的公开页面
SSG最快好最低博客、文档、营销页
ISR最快好低内容定期更新但不需要实时

水合Hydration

定义服务端渲染出的 HTML 只是"死"的静态画面，没有事件响应能力。浏览器下载并执行 JS 后，把事件监听、状态挂到这些已有 DOM 上，让它"活"过来 —— 这个过程叫水合。

为什么重要它解释了 SSR 页面"看起来已经出来了但点不动"的现象。水合需要下载并执行全部 JS，因此是 SSR 性能的主要瓶颈，也催生了岛屿架构（Islands）、流式渲染、部分水合等优化方案。

🧭
怎么选：先问"谁需要看到这个页面的内容"

需要被搜索引擎收录、需要首屏就是完整内容 → SSR 或 SSG。
登录后才可见、不需要 SEO、交互复杂 → CSR 最省事。
内容不常变（文档、官网）→ SSG，性能与成本都最优。
不要一开始就上最复杂的方案：很多项目的正确答案是"营销页静态生成 + 应用页客户端渲染"的混合。

九、分层、抽象与耦合

抽象Abstraction

定义隐藏实现细节，只暴露必要的接口。你调用 db.query() 时并不需要知道磁盘怎么寻道。

性质抽象简化了使用，但增加了理解成本。好的抽象让人不必关心下层；坏的抽象让人不得不"穿透"去看下层到底干了什么 —— 后者在工程里极为常见（比如 ORM 生成了意料之外的 SQL）。

判断标准如果一个抽象让 90% 的场景变简单、10% 的场景变复杂且难以理解，它就是坏抽象。抽象的成本是永久的，收益必须足够普遍。

耦合与内聚Coupling / Cohesion

耦合模块之间依赖的紧密程度。耦合越高，改一个模块越容易牵连其他模块。目标是低耦合。

内聚一个模块内部各元素的相关程度。内聚越高，模块职责越单一、越好理解。目标是高内聚。

一句话"高内聚、低耦合"意味着：相关的东西放在一起，不相关的东西不要互相知道。这两个词是评价任何代码组织方式（分层、组件化、微服务）的通用标尺。

"随意调用"与"分层"的差别
【随意调用：任何代码都能直接碰数据库】
   控制器A ──┐
   控制器B ──┼──→ 数据库
   定时任务 ──┘
   ← 一旦表结构变更，所有调用点都要改
   ← 权限校验、审计日志、缓存逻辑要在每个调用点重复写一遍

【分层：所有访问收敛到一层】
   控制器A ──┐
   控制器B ──┼──→ 服务层（业务规则/事务/权限）──→ 数据访问层 ──→ 数据库
   定时任务 ──┘                ↑
                          缓存、日志、校验都收在这里的少数位置
   ← 表结构变更只需改数据访问层
   ← 换个数据库只改最后一层
   ← 代价：多了一层函数调用、多了一层需要理解的概念

分层的代价

  • 性能开销：每多一层就多一次调用与转换，极端情况下层次过多会让延迟翻倍。
  • 认知开销：新人要理解五层目录才能改一个小功能。
  • 容易出现"贫血层"：某些层只是把参数原样透传，没有实际职责，属于无效抽象。

所以"层数"不是越多越好。正确的判断是：这一层是否承载了独立的职责，且这个职责是否只在这一处被实现。如果两个层做的事完全一样，就合并。

架构的本质Architecture

定义架构是关于"系统由哪些部分组成、部分之间如何交互、以及为什么这样选"的一系列难以更改的决策。

性质① 架构是取舍，不是标准答案 —— 每个选择都在换得某些性质的同时放弃另一些（简单换灵活、性能换成本、一致换可用）；② 架构服务于约束（团队人数、预算、时间、既有技术栈），脱离约束谈架构是空谈；③ 架构会随时间演进，不要一次设计到三年后。

最实用的产出一份架构决策记录（ADR）：每做一个重要选择，用半页纸写下"背景 / 方案 / 决定 / 后果"。这是团队里性价比最高的文档 —— 半年后没人记得为什么当初不用微服务，但文档记得。

🚧
关于"架构"最常见的误解

误解一：架构 = 用高级技术。实际上最简单的单体 + 一个数据库，往往是当前阶段最优的架构。
误解二：架构要一次设计好。实际上过度前瞻设计的部分通常都没用上，还成了负担。
误解三：架构是架构师的事。实际上每写一个函数都在做架构决策（放哪一层、依赖谁），只是粒度不同。

十、一致性、可用性与扩展性

一致性Consistency

定义多个副本 / 多个节点上的数据，在某个时刻看起来是否相同、是否符合预期。

一致性光谱 强一致性：任何时刻读到的都是最新值（代价：必须等所有副本确认，慢且怕故障）； 弱一致性：不保证读到最新值，只保证最终会一致； 最终一致性：短暂不一致可接受，但一段时间后一定会收敛。

举例发朋友圈：自己立刻看到（本地先渲染），别人几秒后才看到 —— 这就是最终一致性在用户体验上的成功应用。而查账户余额必须强一致：显示 100 元却取不出 100 元是不可接受的。

CAP 定理：分布式系统的三选二困境
                      一致性 C
                    （Consistency）
                        ╱╲
                       ╱  ╲
                      ╱    ╲
                     ╱  取舍 ╲
                    ╱   只能  ╲
                   ╱   取两个  ╲
                  ╱____________╲
          可用性 A               分区容错性 P
       （Availability）      （Partition tolerance）

关键理解（很多人在这里理解错了）：
  P（分区容错）不是"可选项" —— 只要系统跨网络部署，网络故障必然发生，
  所以 P 必须接受。真正的选择是在 C 和 A 之间：

  · 选 CP：网络分区时，宁可让部分请求失败，也不返回不一致的数据
           → 典型：银行转账、库存扣减、分布式锁（如 etcd、ZooKeeper）

  · 选 AP：网络分区时，宁可返回旧数据，也要保证服务可用
           → 典型：信息流、点赞数、购物车展示（如 Cassandra、DNS）

现实中的系统通常是"混合"的：同一个应用里，支付走 CP，推荐走 AP。

BASEBasically Available, Soft state, Eventually consistent

定义对 CAP 中 AP 路线的工程化总结：基本可用（允许降级但不停服）、软状态（允许中间态存在）、最终一致（最终收敛即可）。

相对 ACIDACID 追求强一致与即时正确，适合单库事务；BASE 追求可用与扩展，适合跨服务的分布式场景。两者的选择标准是：这笔数据算错会不会造成不可挽回的损失。会，就用 ACID；不会，就可以用 BASE 换性能与可用性。

可用性的度量

几个九可用性 = 可用时间 ÷ 总时间。99.9% 意味着每月最多允许 43 分钟不可用。

关键性质可用性靠冗余换来的：单机永远做不到四个九，因为硬件必然故障。多副本、多可用区、故障自动转移是达到高可用的唯一途径 —— 而冗余意味着成本翻倍，所以要先算清"停机一分钟损失多少钱"，再决定投多少冗余。

链式放大如果页面依赖 5 个服务，每个服务可用性 99.9%，串联后的整体可用性约为 99.5%（每月多出 3 小时不可用）。依赖越多，整体越脆弱 —— 这是"减少依赖与调用链长度"这条架构原则的数学依据。

垂直扩展（Scale Up）

  • 给机器加 CPU、加内存、换更快的磁盘
  • 实现最简单，代码零改动
  • 有物理上限，价格非线性上涨
  • 仍是单点，宕机就是全站宕机
  • 适合：起步阶段、有状态服务（数据库）

水平扩展（Scale Out）

  • 增加更多机器，共同分担流量
  • 理论上无上限，成本线性
  • 前提是服务必须无状态
  • 需要负载均衡、会话外置、部署自动化
  • 适合：无状态的应用服务层

瓶颈与木桶效应

定义系统的整体性能取决于最慢的那个环节。数据库 1 秒、应用 50 毫秒、网络 30 毫秒，整体响应就是 1 秒出头。

实践含义优化必须找当前瓶颈，优化非瓶颈毫无收益。这也是为什么"先测量再优化"不是口号：花一周优化了 30 毫秒的网络，而数据库慢查询占了 900 毫秒，等于白干。

扩容的次序先优化 SQL 与索引 → 加缓存 → 应用多实例 → 读写分离 → 分库分表。每一步都比下一步便宜一个数量级，而绝大多数项目在前两步就够用了。

🎯
原理篇的核心一句话

Web 开发里所有的"最佳实践"，都可以从本篇的原理推导出来： 因为 HTTP 无状态 → 需要 Cookie/Token； 因为网络必然分区 → 必须做冗余与降级； 因为 IO 密集 → 异步优于多线程； 因为抽象有成本 → 层数要克制； 因为资源有限 → 一切优化都要先测量。 记住原理，就不需要背结论。
